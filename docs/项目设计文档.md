# 自动解压处理工具：项目设计文档

## 1. 项目目标

项目用于将下载后的作品包自动整理为统一、干净的 `RJxxxxxxxx` 作品目录，部署位置可自行选择。

总体流程：

```text
拖入文件或文件夹
→ 多层递归解压
→ 整理为 RJ 作品目录
→ 原生 MP3 检测
→ WAV 转 MP3
→ 删除冗余文件
→ 清理空目录
→ 只读查询外置工具缓存
→ 补全 RJ 作品根目录名称
```

## 2. 系统组成

| 文件 | 职责 |
| --- | --- |
| `启动界面.bat` / `启动界面.vbs` | 启动图形界面 |
| `extract-gui.ps1` | 输入、输出位置、进程和日志界面 |
| `processing-pipeline.ps1` | 调度解压、文件处理、名称补全三个阶段 |
| `rename-stage.ps1` / `src/rename_stage.py` | 只读查询重命名工具缓存，补全根目录名称，保存路径映射 |
| `extract.ps1` | 压缩包识别、密码、安全检查和递归解压 |
| `file-process.ps1` | MP3/WAV 判断、转换、删除和空目录清理 |
| `config.json` | 解压、处理和外置工具配置 |
| `解压密码.txt` | 固定密码候选 |
| `logs` | JSONL 运行日志 |

外置转换工具：

- `wav_to_mp3.bat`：安装位置由 `config.json` 的 `plugins.wav_to_mp3.launcher` 指定。
- `wav_to_mp3.ps1`：安装位置由 `config.json` 的 `plugins.wav_to_mp3.script` 指定。

## 3. 图形界面

界面支持：

- 拖入单个或多个文件。
- 拖入单个或多个文件夹。
- 添加、移除和清空输入。
- 停止当前任务。
- 实时显示标准输出和错误日志。

界面不再区分预演和实际执行。点击“开始处理”后直接运行完整工作流。

### 3.1 输出位置

- **解压到指定文件夹**：默认选项，将本次结果统一输出到用户选择的目录。选定后路径立即保存到 `gui-settings.json`，下次启动自动恢复。
- **解压到原地址**：可选模式，每个压缩包分别输出到自身所在目录。

GUI 会先传递 `-Run` 及输出模式，再将所有输入作为连续位置参数传入，避免 `pwsh -File` 吞掉多路径数组后的开关。

## 4. 流水线调度

第三阶段在线数据源优先为 DLsite `maniax/api/=/product.json`，与外置重命名工具的查询入口一致。按 `workno` 精确校验身份，读取 `work_name`、`maker_name` 和 `creaters.voice_by`，允许特典作品没有声优。接口无结果或 404 时才回退至展示页；不能根据展示页 404 判定商品不存在。兼容用户使用外置工具完成改名后的精确路径重新登记。

`processing-pipeline.ps1` 按顺序运行：

1. 递归解压。
2. 读取解压结果清单。
3. 确认本次生成的最终 RJ 目录。
4. 对这些目录执行文件处理。
5. 调用名称补全阶段：只读复用外置工具 `cache.db` 与命名配置，更新结果清单中的实际路径。
6. 在输出父目录保存 `.rj-name-map.json`，记录原始包指纹和本批全部作品路径；重复运行时只有来源指纹一致且结果目录全部存在才复用。文件处理层同时接受纯 RJ 目录和补全标题后的 RJ 目录。

名称补全仅修改作品根目录，不执行外置 EXE，不生成文件夹图标，也不改音轨文件名。默认优先读取外置缓存，未命中时按完整 RJ 号查询 DLsite 官方作品页，验证 canonical 编号和标题，成功结果另存到本工具 `work/naming_metadata.json`。404、网络失败、非法元数据、过长路径、目标冲突时不覆盖原目录，记录待补全；整体提示前两阶段成功、名称部分待补全。第三阶段可以通过 `rename-stage.ps1 -ResultFile <本次结果JSON>` 单独重试。名称日志保存到 `logs/naming_*.jsonl`；支持模板字段 `rjcode`、`work_name`、`cv_list_str`、`maker_name`。

任一压缩包解压失败时，不启动 WAV 转换或后续删除，流水线返回非零退出代码。

## 5. 输入与压缩包识别

### 5.1 直接拖入文件

每个直接拖入的文件都无条件作为初始压缩包起点，不会因扩展名、无扩展名或文件头未知而静默跳过。最终由 7-Zip 判断是否可解压。

支持的输入形式包括：

```text
archive.7z
archive.zip
archive.rar
archive.exe
archive.7zkkk
archive.99
archive
```

若文件实际不是压缩包，7-Zip 会明确报错并计入失败。

正式执行时，无扩展名压缩文件会按真实文件头补上 `.7z`、`.zip`、`.rar`、`.gz` 或 `.exe`，从而释放原文件名给最终同名 RJ 目录。

### 5.2 拖入文件夹

对文件夹进行递归扫描时，仍根据扩展名和真实文件头识别压缩包，防止将普通图片、音频和文档都当成压缩包。

文件头识别包括 7z、ZIP、RAR、GZip 和 PE/SFX。支持无扩展名、伪装扩展名以及 `.7z.001`、`.zip.001`、`.part1.rar` 等分卷起点。

DOCX、XLSX、PPTX、OpenDocument、EPUB、APK 和 JAR 等文件虽使用 ZIP 容器，但在内层递归扫描中明确排除。用户若直接拖入这些文件，仍遵循“直接拖入必入队”规则。

日文 ZIP 文件名使用 `extraction.zip_filename_code_page = 932` 指定 Shift-JIS/CP932 代码页。密码测试、安全目录检查和正式解压使用同一代码页，以保证实际文件名与预检结果一致。

## 6. RJ 编号与密码

系统从文件名、完整路径和父目录提取所有完整 RJ 号。纯 7–8 位数字文件名会自动补全：

```text
01694773 → RJ01694773
1700447  → RJ01700447
```

密码候选顺序：

1. 文件名和父路径中的完整 RJ 号。
2. RJ 号的大写与小写形式。
3. 纯数字文件名补全的 RJ 号。
4. 本地缓存和 DLsite 模糊补全候选。
5. `解压密码.txt` 中的固定密码。

如果压缩包目录本身可见，系统还会提取包内路径中的所有 RJ 号作为补充密码。这用于单个外包同时容纳多个 RJ 作品、且数据加密但目录未加密的情况。

文件名提取不依赖网络或缓存。日志不写入实际密码，只记录成功候选的序号。

## 7. 递归解压

最大递归深度默认为 30 层。只要当前解压结果中仍存在压缩包，就继续处理，直到：

- 不再存在内层压缩包。
- 达到最大深度。
- 解压失败。
- 触发安全预算。
- 输出目录发生冲突。

分卷包只以第一卷作为任务起点，其余分卷由 7-Zip 自动读取。

## 8. 解压安全约束

`config.json` 中的主要安全限制：

- 最大递归深度：30。
- 最大预计展开容量：当前为 `0`，表示不限制。路径越界、文件数量和普通程序保护仍然启用；该设置可能导致磁盘被大型或恶意压缩包占满。
- 最大文件数：200,000。
- SFX 只交给 7-Zip 读取，不执行。
- 解压失败不删除原包。
- 同名输出目录存在且无完成标记时，拒绝覆盖或制造时间戳副本。

失败现场通常保留为 `文件名.__extracting__`。

## 9. 压缩包保留与删除

- **最外层原始压缩包**：始终保留。
- **中间压缩包**：成功展开后永久删除，不再移入隔离区。
- **中间分卷包**：成功展开后删除同组全部分卷。
- **最终内层压缩包**：内容成功提交后删除。
- **失败的压缩包**：不删除。

当前配置：

```json
"keep_original_archives": true,
"intermediate_archive_action": "delete",
"nested_final_archive_action": "delete"
```

## 10. 最终 RJ 目录

系统会剥离纯包装层和 `_temp` 层，最终整理为：

```text
输出位置
└─ RJ01673643
   ├─ 作品内容
   ├─ 音频
   ├─ 图片
   └─ .extract_complete.json
```

`.extract_complete.json` 用于表明该目录已由工具完整生成。RJ 作品根目录在文件处理阶段永远不会被删除。

## 11. 作品边界

文件处理以每个 `RJxxxxxxxx` 目录为独立作品。不同作品之间：

- 不共享 MP3 候选。
- 不交叉匹配 WAV。
- 不跨作品删除重复文件。
- 不共享版本判断。

父目录中包含多个 RJ 目录时，系统会将它们拆分为多个独立作品。

## 12. WAV 与原生 MP3

### 12.1 作品完全没有 MP3

该作品的全部 WAV 进入 320 kbps MP3 转换队列。MP3 格式和时长校验成功后删除 WAV；转换或校验失败时保留 WAV。

### 12.2 作品已存在 MP3

系统会在整部作品范围内寻找对应的原生 MP3，不要求 WAV 与 MP3 位于同一文件夹。

匹配信号：

- 音频时长。
- 轨道编号。
- 多层目录结构和版本上下文。
- 有无效果音。
- 有无 BGM。
- 音声-only 等变体标记。
- 标准化文件名，仅作辅助，不要求完全相同。

明确版本冲突或多个候选无法唯一确定时，不冒险删除 WAV，而是进入转换队列。

## 13. 版本语义和原生轻量版

系统区分普通本篇、`MP3軽量版`、`SEなし`、`SEあり`、`BGMなし`、`BGMあり`、音声-only、特典等内容分支。语义明确冲突时禁止跨版本匹配。

如果作品同时存在原生 `MP3軽量版` 和 WAV 后转得到的普通本篇 MP3，系统优先保留原生轻量版。

整组版本匹配使用：

- 内容分支和目录语义。
- 曲目数量。
- 整组时长集合。
- 轨道编号。
- 一对一覆盖关系。
- 文件名辅助分数。

只有后转版本的全部曲目都能被可靠覆盖时才删除。`SEなし`、`BGMなし` 和特典等独立版本继续保留。

原生 MP3 不要求达到 320 kbps；只要格式可读、时长匹配并且版本判断可靠，即优先保留。

## 14. MP3 转换与删除安全

外置 BAT 在自动模式下递归扫描作品目录，将剩余 WAV 转换为 320 kbps MP3，不等待人工输入或暂停。

WAV 只在以下条件全部成立时删除：

```text
目标 MP3 已存在
+ MP3 可以正常读取
+ 编码格式确实是 MP3
+ MP3 与 WAV 时长一致
```

任一步失败都保留 WAV、记录错误并返回失败状态。

## 15. MP4 删除

文件处理阶段递归删除每部作品中的 `.mp4`。删除失败时写入日志并计入任务失败。

## 16. 空目录清理

WAV 目录是否可删除以处理前的文件快照为准：

- 原本完全由 WAV 构成的目录，WAV 全部成功处理后可删除。
- 目录或其子目录原本存在任意非 WAV 文件时，该目录标记为受保护，不允许因 WAV 清理而删除。
- 删除重复 MP3 或 MP4 后，只删除真正为空的目录。
- RJ 作品根目录永远保留。

空 WAV 目录删除由 `processing.delete_empty_wav_directories` 控制，默认启用。因此 `wav`、`SEなしwav` 等纯 WAV 版本目录会在音频成功处理后连同文件夹删除。

对处理前完全没有 MP3 的天生纯 WAV 作品，`processing.preserve_wav_directories_when_work_has_no_mp3` 默认为 `true`。系统会显式保护其原始 WAV 目录：WAV 转换成功后可删除，但目录和同位置新生成的 MP3 保留。

## 17. 日志

项目日志位于项目根目录的 `logs` 文件夹，主要包括：

```text
extract_时间.jsonl
file_process_时间.jsonl
```

外置 WAV 转换日志位于该转换脚本所在目录的 `logs` 文件夹。

日志记录输入、压缩包类型、递归深度、预计大小、解压结果、密码候选序号、最终 RJ 目录、中间包删除、音频匹配、转换和文件删除结果。日志不包含真实密码。

## 18. 当前总体原则

```text
最外层原包保留
中间压缩包成功展开后删除
最终内层压缩包成功提交后删除
任一解压失败则不启动文件处理
原生 MP3 优先保留
没有可靠原生 MP3 才转换 WAV
MP3 验证成功后才删除 WAV
MP4 永久删除
原本含任意非 WAV 文件的目录不因 WAV 清理而删除
不同版本和不同 RJ 作品禁止混合匹配
```
