# 自动解压处理工具：方案研究

## 1. 需求理解

工具监控一个或多个下载目录。发现下载完成的资源后，先解压到独立的临时工作区，再按规则处理文件，最后将结果移动到输出目录。

初步规则：

1. `.wav` 转换成 `.mp3`；验证 MP3 可读取且时长合理后，移除 WAV。
2. `.vtt` 转换成 `.lrc`；验证 LRC 有合法时间标签后，再移除源文件。
3. `.mp4` 移入隔离区，确认无误后再清理。
4. 其他文件默认原样保留。

原需求中的“VTT 转换为 LRC 并删除 LRC”存在歧义。较常见的目标是删除转换前的 VTT，因此设计为配置项 `delete_vtt_after_success`，在确认前不会硬编码删除哪一种文件。

## 2. 推荐处理流水线

```text
下载目录
  -> 判断文件是否下载完成
  -> 建立本次任务和临时目录
  -> 安全解压
  -> 扫描全部文件（可选递归处理嵌套压缩包）
  -> 根据规则转换、保留或隔离
  -> 校验输出
  -> 提交到最终目录
  -> 写入任务日志和处理记录
```

所有转换都应采用“先生成临时目标文件，校验成功，再原子改名”的方式。任何一步失败都保留源文件，并将任务标记为失败或需人工检查。

## 3. 下载完成判定

仅凭文件出现就开始解压容易读到尚未下载完的文件。建议同时满足：

- 文件名不是 `.crdownload`、`.part`、`.tmp` 等临时后缀。
- 文件大小和最后修改时间连续若干次检查均未变化，例如每 3 秒检查一次，连续 3 次稳定。
- 文件可以被独占或只读打开。
- 对压缩包进行快速完整性检查后再进入正式流程。

首版可采用定时扫描，逻辑简单且可靠；后续需要更快响应时再加入文件系统事件监听。

## 4. 解压策略

### 第一阶段

- `.zip`：Python `zipfile`。
- `.tar`、`.tar.gz`、`.tgz`：Python `tarfile`。

### 扩展阶段

- `.7z`、`.rar`：调用 7-Zip 命令行程序。
- 密码压缩包：从任务配置或交互输入密码；禁止把密码明文写入普通日志。
- 嵌套压缩包：设置最大层数和最大展开体积，避免无限递归和压缩炸弹。

解压前必须阻止路径穿越：压缩包内的绝对路径或包含 `..`、盘符、网络路径的条目不能写出任务临时目录。

## 5. WAV 转 MP3

本机已有 FFmpeg，可使用 `libmp3lame` 编码。建议默认采用 VBR 质量模式，而不是固定码率：

```text
ffmpeg -i input.wav -map_metadata 0 -codec:a libmp3lame -q:a 2 output.tmp.mp3
```

建议校验条件：

- FFmpeg 退出码为 0。
- 输出文件存在且非空。
- `ffprobe` 能识别音频流。
- 输出时长与输入时长差异在允许范围内。

只有全部通过后才将临时文件改名为正式 `.mp3`，并按配置将 WAV 移入隔离区。

如果同名 MP3 已存在，默认不要覆盖；可以选择跳过、自动加序号，或在哈希相同的情况下视为已完成。

## 6. VTT 转 LRC

转换器需要处理：

- `WEBVTT` 文件头与注释块。
- `hh:mm:ss.mmm --> hh:mm:ss.mmm` 时间范围。
- 多行字幕合并。
- HTML/样式标签清理。
- 重复时间戳、空字幕和无效时间。
- UTF-8、UTF-8 BOM 与常见编码异常。

基础映射示例：

```text
00:01:12.340 --> 00:01:15.000
第一行
第二行

转换为：
[01:12.34]第一行 第二行
```

普通 LRC 主要记录每句开始时间，VTT 的结束时间通常不写入。转换完成后至少要确认文件包含合法的 `[mm:ss.xx]` 标签并且时间顺序合理。

## 7. 删除与恢复策略

不建议首版直接永久删除。推荐三档策略：

- `dry_run`：只打印将要执行的动作，不改动文件。
- `quarantine`：把待删除文件移动到项目隔离目录，保留若干天。
- `permanent`：永久删除，只在规则经过充分验证后启用。

删除的前置条件：

- WAV/VTT 只有在对应目标转换并校验成功后才能移除。
- MP4 可直接进入隔离区，但要记录原始路径、大小、时间和任务编号。
- 解压失败、转换失败或目标冲突时，一律不删除源文件。

## 8. 建议配置结构

```yaml
watch:
  folders:
    - "D:/Downloads"
  scan_interval_seconds: 5
  stable_checks: 3

output:
  folder: "D:/Processed"
  preserve_subfolders: true

archive:
  delete_after_success: false
  nested_max_depth: 2
  max_expanded_size_gb: 20

rules:
  wav_to_mp3:
    enabled: true
    quality: 2
    delete_wav_after_success: true
  vtt_to_lrc:
    enabled: true
    delete_vtt_after_success: true
  mp4:
    action: quarantine
  unmatched:
    action: keep

safety:
  mode: dry_run
  quarantine_days: 7
  overwrite_existing: false
```

上述内容是设计草案；正式实现时可用 YAML，也可以为减少依赖改用 TOML。

## 9. 状态、日志与幂等性

建议用 SQLite 保存任务状态，至少记录：

- 输入路径、文件大小、修改时间与可选哈希。
- 解压、转换、校验、隔离的每一步结果。
- 输出文件路径和错误信息。
- 任务开始与结束时间。

这样程序重启后可以继续未完成任务，也能防止同一文件被重复处理。文本日志用于排错，SQLite 用于可靠状态管理。

隔离文件和运行日志应加入版本控制忽略列表。开发测试必须使用复制出来的样本，不能直接使用唯一一份下载资源。

## 11. 分阶段实施建议

### 阶段 A：可验证的命令行原型

- 接收单个压缩包或目录。
- 支持 ZIP/TAR。
- 实现 WAV→MP3、VTT→LRC、MP4 隔离。
- 默认预演，输出清晰的处理计划。
- 建立单元测试和含异常文件的测试样本。

### 阶段 B：自动监控

- 监控下载目录并判断下载完成。
- SQLite 任务记录、失败重试和冲突处理。
- 支持 RAR/7Z、嵌套压缩包和密码包。

### 阶段 C：易用性

- Windows 托盘图标、暂停/继续、最近任务列表。
- 规则编辑与目录选择界面。
- 打包为可独立运行的 EXE。

## 12. 开发前需要确认的选项

1. VTT 转 LRC 后究竟删除 VTT，还是删除新生成的 LRC。
2. 原压缩包在全部处理成功后保留、隔离，还是永久删除。
3. 实际下载目录和最终输出目录。
4. MP3 使用高质量 VBR，还是指定固定码率（如 320 kbps）。
5. 是否需要支持 RAR、7Z、密码压缩包与嵌套压缩包。
6. MP4 是否一律移除，还是某些目录或文件名需要例外。

在这些选项确认前，可以先实现全程 `dry_run` 的原型，不触碰原文件。
